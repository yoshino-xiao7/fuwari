## # 前言：游戏没怎么玩，图倒是画了一堆

这个周末基本都在折腾雪涼云的 AI 绘画功能。

先把时间说清楚一点：我写这篇的时候是周日晚上，所以文里的“昨天”就是周六，也就是 Beta1；“今天”就是周日，也就是 Beta2。

昨天先把 AI 绘图 Beta1 做出来，让基础链路能跑通；今天继续做 Beta2，把重点放在双角色绘制、服务状态、提示词生成和角色预设这些体验上。

本来还想着周末多少玩会游戏，结果一坐到电脑前就是 ComfyUI、Worker、LoRA、prompt、双角色、区域控制、前端页面、后端队列，从昨天折腾到今天，游戏没怎么碰，代码倒是改了一堆。

虽然过程挺折磨，但现在回头看，效果还算可观。

昨天的 Beta1 解决的是“能不能跑起来”：用户提交任务，本机 Worker 领取，ComfyUI 出图，云端保存到 OSS，用户在历史里查看。

今天的 Beta2 主要解决的是“怎么稍微好用一点”：服务状态要看得到，提示词生成要更可靠，LoRA 和角色预设不能再靠一个冷冰冰的下拉框，双角色绘制也要先有个能用的雏形。

---

## # 双角色绘制：能用，但还很 Beta

今天这轮 Beta2 最主要的更新是 **双角色绘制**。

单角色绘制相对好办。选一个角色预设，注入一组 tags，挂一个 LoRA，再配合正向提示词和反向提示词，生成结果不一定每次都完美，但至少方向比较明确。

双角色就完全不是一个难度了。

现在前端可以在单角色 / 双角色之间切换。双角色模式里可以选择：

- 角色 A 预设。
- 角色 B 预设。
- 第一 LoRA。
- 第二 LoRA。
- 第二角色 ID。
- 可选角色布局参考。

普通用户双角色按两张图计费，也就是 `100` 积分；管理员仍然免费。

目前双角色属于“勉强能用”的状态。如果提示词写得好，角色选择合适，LoRA 强度控制住，效果确实能出来，而且有时候还挺惊喜。但它还远没有到稳定、傻瓜式、随便点两下就出好图的程度。

## # 遇到的离谱问题

今天做 Beta2 时，最让我头疼的就是双角色各种奇怪 bug。

最开始我以为：既然可以加载两个 LoRA，那是不是给 A 一个区域、给 B 一个区域，再让模型按区域画就好了？

事实证明没那么简单。

实际测试里遇到过这些问题：

- 两个角色直接融合成一个人。
- A 的发色跑到 B 身上，B 的服装又跑到 A 身上。
- 明明想画两个人，结果只剩一个角色。
- 第二角色被默认构图遮挡。
- 左右两侧各自生成两个人，画面变成四个人。
- 手脚数量开始自由发挥。
- 用户手绘的区域或遮罩反而污染了最终画面。
- 遮罩边缘、布局线索和角色 tags 互相打架。

有些问题看起来甚至很荒唐：你以为自己在帮模型“规定位置”，结果模型把这部分当成画面内容的一部分理解了，最后生成效果反而更乱。

所以最后默认策略改了。

现在默认不再把用户画的 A/B 区域当作真实 mask，也不默认走二次 inpaint。它只会提取一个大致布局关系，比如谁在左、谁在右、谁更靠近，然后转成普通布局提示词。

也就是说：手绘区域现在更像“构图参考”，不是“精准分割遮罩”。

这比一开始想象的方案保守，但稳定一点。

## # 为什么不用强区域控制当默认

我也试过区域 mask、inpaint、conditioning 这些方案。

理论上它们看起来很美好：左边给角色 A，右边给角色 B，然后两个区域各自使用对应 LoRA。实际落地时，基础 ComfyUI 节点对多角色 LoRA 的区域隔离并不够理想。

问题在于，双角色不是简单把两张单人图拼在一起。

角色 tags、LoRA 权重、构图、动作、遮挡、身体朝向、镜头距离都会互相影响。尤其是动漫模型里，角色特征本来就很强，两个 LoRA 同时上场时，串味很容易发生。

所以 Beta2 先选择更稳的默认策略：

- 双角色 prompt 自动过滤 `1girl`、`solo` 这类单角色 tags。
- 默认降低双角色 LoRA 强度上限。
- 不默认启用区域 conditioning。
- 不默认启用二次 inpaint。
- 手绘区域只转成布局提示。

后续如果继续优化，可能要接入 attention couple、regional LoRA 之类的自定义节点，或者引入自动分割后的局部修复流程。那就是下一阶段的事情了。

## # LoRA 和角色预设也补了一点

除了双角色，今天也补充了一小部分新的角色 LoRA 和预设。

目前整理进去的角色包括：

- 卡提希娅。
- 八重神子。
- 雷电将军。
- 桑多涅。
- 哥伦比亚。
- 茜特菈莉。

每个角色预设会尽量包含：

- 中文显示名。
- 角色分类。
- LoRA 文件名。
- 推荐 LoRA 强度。
- 触发词。
- 默认注入 tags。
- 预览图。
- 推荐 checkpoint。

这部分还远远不够。

AI 绘图真正好用起来，很大一部分体验其实不在“按钮能不能点”，而在于预设够不够好。用户不应该每次都去翻 LoRA 文件名、查触发词、试强度。理想状态是点一个角色卡片，基础 tags、LoRA、强度、推荐模型都自动带出来，然后用户只需要补场景和动作。

这轮只是先补了一点点，后面还会继续加。

## # 提示词生成也换成了本机 Ollama

之前自然语言提示词生成效果不太稳定。

Beta2 里改成了由本机 Worker 领取提示词翻译任务，再调用本机 Ollama 生成英文正向/反向提示词。云端只负责任务排队和结果回写，不直接生成。

同时给本机加了一个提示词知识库：

```text
setu_ai_wife/config/prompt_knowledge.json
```

它主要用来补充角色名、作品名、别名和一些常见 tag 上下文。

这样至少可以减少一种很尴尬的情况：用户输入中文角色名，最后正向提示词里还原封不动地塞着中文，模型完全不知道该怎么画。

不过这块也还在 Beta。Ollama 不会永久学习，知识库只是每次请求时注入上下文，不会改变模型权重。所以它能帮忙，但不能指望它突然变成完美 prompt 工程师。

## # 服务状态终于能看见了

Beta1 时还有一个体验问题：用户不知道 AI 服务到底能不能用。

现在前端会展示服务状态：

- Worker 是否在线。
- 当前是否开放。
- 开放时间。
- 队列数量。
- 运行中数量。
- 上传中数量。
- 预计等待时间。
- 不可用原因。

Beta 开放时间暂定：

```text
08:30-22:30
```

普通用户需要在开放时间内使用，管理员只要 Worker 在线就能用。

这主要是因为现在还是拿闲置电脑跑 Worker，不是正式 GPU 服务。要给它留一点休息空间，也要避免我不在的时候出问题没人处理。

## # 现在的效果

目前双角色已经能出图了。

如果提示词写得比较明确，比如角色 tags、站位、动作、场景都写清楚，再控制好 LoRA 强度，结果是可以看的。

但如果 prompt 太含糊，或者两个角色的特征太强、服装太复杂、构图遮挡太严重，就还是会出现串味、融合、角色不完整之类的问题。

所以我现在对它的定位是：

**Beta，但值得继续优化。**

它已经不是完全不能用的实验玩具，但也还不是可以放心交给所有用户随便玩的成熟功能。
