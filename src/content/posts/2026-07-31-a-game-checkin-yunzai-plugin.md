## # 前言：不想再为每个游戏装一套签到插件

最近在开发一个新的 Yunzai 插件：**A-game-checkin**。

它的目标很直接——把不同二游社区的每日签到统一到一个插件里。用户不需要记住每个社区不同的绑定方式，也不用为每款游戏单独寻找、安装和配置插件；绑定社区账号后，插件会自动发现账号下的游戏角色，并负责之后的每日签到。

第一阶段已经接入了三个社区：

- **米游社**：原神、崩坏 3、崩坏学园 2、未定事件簿、崩坏：星穹铁道、绝区零。
- **森空岛**：明日方舟、明日方舟：终末地。
- **库街区**：战双帕弥什、鸣潮。

目前插件可以运行在 **Yunzai v3、Miao-Yunzai 和 TRSS-Yunzai**。从最初的想法到现在，主体功能已经基本落地，这篇就记录一下这一阶段做了什么，以及后面准备把它扩展成什么样子。

---

## # 为什么要做统一签到

二游的社区签到并不是什么新功能，但真正用起来时，体验往往比较零散。

米哈游的游戏在米游社，鹰角的游戏在森空岛，库洛的游戏又在库街区。不同社区有自己的登录方式、账号结构、接口规则和风控逻辑。对于同时玩几款游戏的人来说，每天挨个打开 App 签到很麻烦；对于机器人开发者来说，为每个游戏维护一套重复的绑定、定时任务和消息卡片也不太优雅。

所以这次没有按“一个游戏一个插件”的思路去做，而是把**社区**作为接入边界：

```text
Yunzai 命令
    ↓
统一签到协调层
    ↓
米游社 / 森空岛 / 库街区适配器
    ↓
各社区下的游戏与角色
```

社区自己的凭证、接口和错误码都留在适配器内部，核心逻辑只关心几个统一的问题：

- 这个账号下有哪些角色？
- 哪些角色开启了自动签到？
- 今天是否已经签到成功？
- 实际拿到了什么奖励？

这样以后继续接入新社区时，不需要重新写一遍账号管理、定时任务、日志和卡片系统，只要补充新的社区适配器即可。

## # 绑定一次，自动发现账号里的游戏

这次最希望做好的体验，是尽量减少手动配置。

用户绑定社区账号后，插件会自动发现该账号下的游戏角色。新发现的角色默认开启自动签到，并在每天 `09:00`（`Asia/Shanghai`）执行。调度器每 10 分钟扫描一次待执行任务，同时按业务日期记录签到结果，避免同一个角色当天重复签到。

当然，自动签到也可以按角色单独暂停。即使关闭了自动签到，仍然可以随时手动执行，不会因为订阅状态而被拦住。

手动签到支持按游戏名称、别名或卡片编号选择。账号编号和游戏编号分开处理，卡片里也会展示稳定编号，尽量避免多账号、多角色时出现“到底签的是哪一个”的歧义。

除了签到以外，目前还完成了：

- 查看已经绑定的社区账号。
- 查看自动发现的游戏与角色。
- 一键执行全部签到。
- 查询签到日志和奖励记录。
- 开启或暂停单个角色的自动签到。
- 删除社区账号，并通过 60 秒二次确认避免误操作。

整体思路就是：第一次绑定稍微花一点时间，之后尽量让它安静地自动运行。

## # 三个社区，三套完全不同的登录方式

真正麻烦的部分并不是定时签到，而是如何把三个社区差异很大的登录流程放进 QQ Bot 的交互里。

### 米游社：扫码为主，Cookie 兜底

米游社支持 App 扫码登录，同时保留 Cookie 绑定作为备用入口。

扫码对于普通用户更友好，不需要学习如何抓取 Cookie；Cookie 入口则方便已经熟悉相关工具的用户。在签到结果处理上，也对“今天已经签到”做了统一归一化，避免社区接口返回重复签到时，被插件错误显示成失败。

### 森空岛：短信验证码与 Token

森空岛支持手机号加短信验证码登录，同时保留 Token 绑定。

开发时还遇到了登录换取凭证时签名 Token 缺失的问题。现在插件会在需要时主动刷新凭证，并统一识别重复签到响应。奖励解析也根据资源类型做了适配，能够正确展示明日方舟签到奖励的图标。

### 库街区：最特别的一次性登录页

库街区的手机号登录要处理极验验证，这对没有公网地址的 QQ Bot 来说比较棘手。

最后采用的方案是：机器人生成一个**一次性本地 HTML 页面**，用户用浏览器打开，在页面里完成极验，并由浏览器直接请求库洛官方接口发送验证码。

这个页面有效期只有 10 分钟，不需要给机器人配置公网 IP、域名或内网穿透。登录成功后，插件只保存用户 ID、Token 和设备标识，不会保存手机号、短信验证码或极验结果。

它不算最简单的实现，但对部署者很友好：装好插件就能用，不需要额外搭建一套 Web 服务。

## # 签到成功之外，我还想知道拿到了什么

如果机器人只回复一句“签到成功”，功能当然也能用，但总觉得少了点东西。

所以这次把签到奖励也完整记录了下来。每条日志除了社区、游戏、角色和签到状态，还会保留当天实际获得的奖励名称、数量与图片地址。查看结果时，插件会生成奖励卡片，而不是只发一串文本。

目前一共做了四类图片卡片：

- 账号卡片。
- 游戏与角色卡片。
- 帮助卡片。
- 签到奖励卡片。

几类卡片共用一套玻璃质感和背景遮罩样式，并为不同游戏准备了对应的主题背景。远程奖励图加载失败时会使用独立占位图；对于早期没有奖励明细的历史记录，也会明确说明数据缺失，不会为了让卡片好看而伪造奖励。

我一直觉得，QQ Bot 插件除了“能返回数据”，展示也很重要。一张信息层级清楚的卡片，比十几行挤在一起的文本更容易让人看懂，也更像一个完整的产品。

## # 凭证不能为了方便就明文保存

多社区插件必然要保存 Cookie、Token、用户 ID 和设备标识。如果这些数据直接写进 JSON，一旦服务器文件泄露，绑定的社区账号也会跟着暴露。

A-game-checkin 使用 **AES-256-GCM** 加密这些凭证，并要求部署者设置 `A_GAME_CHECKIN_MASTER_KEY`。如果没有配置主密钥，插件会直接拒绝保存凭证，不会悄悄降级为明文。

这也意味着迁移或备份时，必须同时保留：

```text
data/
A_GAME_CHECKIN_MASTER_KEY
```

只备份数据文件而丢失密钥，原有凭证将无法恢复；只有密钥而没有数据文件也同样没用。

账号、角色、签到订阅和日志目前使用 JSON Store 持久化。对于现阶段的 Yunzai 插件规模来说足够简单，也方便部署与迁移。配置则采用默认值和本地 `config/config.json` 深度合并，可以调整签到时间、时区、重试、退避、日志保留天数以及社区开关。

## # 第一阶段的完成度

截至 2026 年 7 月 31 日，这一轮已经完成了插件主体、三个社区适配器、账号与角色管理、自动和手动签到、凭证加密、奖励日志以及四类图片卡片。

当前自动化验证包括：

```bash
npm test
npm run check
```

共 23 项自动化测试通过，同时完成了主要入口文件的静态语法检查。测试覆盖了签到日期幂等、手动签到、三社区角色发现与登录、奖励归一化、卡片数据构建以及凭证加解密。

不过社区接口和风控规则随时可能调整，模拟响应通过并不等于真实环境永远稳定。接下来仍然需要继续观察真实账号下的登录、Token 刷新、签到响应和图片渲染，尤其是远程图片加载和长列表卡片的表现。

## # 后续计划：从签到插件走向二游社区助手

签到只是这个插件的第一步。

接下来最想做的是**各个游戏前瞻兑换码推送**。现在很多游戏会在版本前瞻、直播或社区活动期间放出限时兑换码，但有效期通常不长，很容易因为没看直播或忘记兑换而错过。

后续计划让插件自动收集并识别不同游戏的前瞻兑换码，再推送到订阅的群或用户。理想状态下，用户不需要一直盯着各个平台：有新兑换码时机器人主动提醒，同时标明所属游戏、兑换内容、有效期和兑换入口。

另一条主线是继续接入**更多社区和更多游戏**。

现在的社区适配器结构已经为扩展预留了位置。后续会根据接口稳定性、登录可行性和实际需求，逐步把更多二游社区纳入同一套账号、订阅、通知和卡片体系。除了每日签到，也可以继续扩展：

- 前瞻直播与兑换码推送。
- 版本更新和维护提醒。
- 体力、每日任务等游戏状态通知。
- 社区公告与活动信息聚合。
- 更完整的角色与账号信息查询。

我希望它最后不只是一个“每天帮你点一下签到”的工具，而是一个统一的二游社区入口：绑定一次账号，剩下的信息提醒和日常操作都尽量交给机器人。

---

## # 小结

A-game-checkin 的第一阶段，本质上是在解决一个很朴素的问题：**玩的游戏越来越多，但每天不该把时间浪费在重复打开社区 App 上。**

从米游社、森空岛到库街区，三个社区背后是完全不同的登录方式、凭证体系和接口规则。把它们接进同一个 Yunzai 插件，比单独做一个签到命令麻烦得多，但统一之后，新增游戏和社区的成本也会越来越低。

目前签到主链路已经跑通，下一步就是继续验证稳定性，并开始推进前瞻兑换码推送与更多社区游戏接入。

先把每天的签到交给机器人，之后再让它帮我们记住那些容易错过的兑换码和活动。
