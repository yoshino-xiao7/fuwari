## # 前言

先说结论，免得你们往下看半天：**DeepSeek 宠物做砸了**。昨天把开发重心放在宠物区，认真设计了平台、写了原型、跑了编码实验，最后发现没有一个方案能跨过"低成本 × 高质量"这道坎。暂停了，代码归档，路线图里也把它删了。今天 v0.2.2-beta.1 照常发布。

这篇主要是记录这次失败——花了那么多时间，宠物功能一行都没上线。顺便交代一下今天发布的东西和新方向。

## # 宠物原本想做成什么样

从第一天的路线图起，"DeepSeek 宠物"就挂在上面，状态一直是"开发中，等角色素材冻结"。Companion 的非宠物阶段收口之后，昨天正式开搞。

而且我给自己定的目标不是"做个能动的小人"，是一个完整平台：

- **声明式宠物包**（`.yukipet` v1）：描述角色和支持的语义动作，不携带可执行代码，应用校验后导入；
- **语义动作**：打瞌睡、睡觉、醒来、揉眼睛、"疯狂进食 token"，由应用状态机触发，用户不能自定义动作语义；
- **创作者输入**：普通用户只需要给角色参考图 + 一句自然语言描述，不需要懂动画软件、骨骼绑定、状态机——剩下的交给**宠物制作 Skill**（一个面向 Codex 的自动化工作流）生成、验证、打包。

方案文档写了 925 行，还配套两个 ADR：用户宠物作为校验过的声明式包交付、通过 creator-first 门禁选择宠物运行时。

## # 昨天到底干了什么

- **925 行的 `docs/11-pet-platform-plan.md`**：宠物平台、包格式、动画、Skill 的完整设计。
- **两个 ADR**：声明式宠物包 + creator-first 运行时选择门禁。
- **原型 1：`pet-runtime-spike`**。对比 Rive、dotLottie、透明 WebM、高密度序列帧四个候选运行时。评测规则苛刻得离谱：相同场景、相同 Creator Input hash、相同 viewport、相同打包环境才能进 benchmark，缺字段、口径不一致直接拒绝比较——就是不想让"看起来高分"的假数据混进来。
- **原型 2：语义宠物 v1 资产实验**。真实生成精灵图集做编码测试：webp 128px / 160px、30fps，quality 95 的 standing 动作源素材 8.6MB，编码后 1.8MB。一堆变体被 reject：双向混合、独立缩放、裁切姿势、缩放比例……每个被拒的变体都留了记录。

## # 为什么没做成：低成本 × 高质量，没有解

我给自己立的两个约束，单看都合理，放一起就是死局：

- **高质量**：宠物必须流畅。方案里白纸黑字写了"**不采用稀疏姿势轮播冒充流畅动画**"——姿势轮播是省事，但那不是动画，是幻灯片。
- **低成本**：不能依赖专业动画师逐帧精修，也不能要求用户会任何动画工具（这是平台设计的前提）。

于是两条路都走不通：低成本路径（姿势轮播、低帧率图集、廉价制作管线）过不了质量关；高质量路径（连续动画资产、专业制作）成本压不下来，还得长期维护多套 player。

试了一圈，确认没有能跨过这道坎的方案。与其硬做一个"能动的贴图"砸招牌，不如先不做。

## # 归档：代码进冷备份，防误恢复

宠物代码全部提交到冷备份分支 `yukiryou/pet-experiment-archive-20260820`（归档提交 `a05117e`）。

归档的同时，我在 AGENTS.md 和 CONTEXT.md 里给这个分支加了保护条款：

- 禁止自动合并、变基、挑拣、作为开发基线、进入发布构建；
- 只有我本人在当前对话里明确要求恢复宠物开发，才能创建新分支按获批范围选择性恢复；
- "继续""推进下一阶段""完成路线图"这类泛化指令**不构成**恢复授权的依据。

加这条是有原因的：这种"做了一半的雄心勃勃分支"最容易在以后的某次自动化里被稀里糊涂捡回来，变成主线里甩不掉的包袱。冷备份就是冷备份。

## # 今天：v0.2.2-beta.1 发布 + 转向

失败归失败，产品线照常走。今天早上发布了 **v0.2.2-beta.1**（Harness `0.1.0-rc.8`）：

- rc.8 带来了原生多模态、`/goal` `/plan` 图文输入、文件/会话引用和可安装的 Profile Bundle 子代理；
- rc.7 → rc.8 **存储格式不兼容**，首次启动会自动保留完整 rc.7 Runtime Home 副本做回退点；
- 固定端口加了 HMAC secret 持有证明——本地其他服务抢了端口也不能冒充 Harness；
- 修了升级后进空会话的问题、启动页品牌图路径问题。

而"转向其他新的方面"，其实就是一条大决定：**接受 ADR 0004，走 Plugin-first 架构**。

之前为了做窗口、更新、工作区审阅、模型能力，我一直在给 Harness 打版本限定的 DOM/编译产物补丁。补丁能解决问题，但每升一次 Harness 都要复核，成本越滚越高。ADR 0004 定了新原则：

1. 产品 UI 优先实现为 Harness 官方插件，走加法型 slot；
2. Electron 双/单 webContents 的载体切换收敛到 main 层 `DesktopProductCarrier`；
3. 根布局 composition 交给 Runtime 的 `DesktopFramePlugin`，不碰 Electron 窗口；
4. 文件、Git、PTY、签名、更新继续留在原生模块，通过窄的、类型化的 preload bridge 提供；
5. 新功能若没有官方 seam，宁可推动上游或保持关闭，**不再用 DOM 猜测快速绕过**。

配套路线图也更新了：**插件市场**（冻结依赖图 + registry provenance/integrity 之后才开放安装）和 **Windows 11 x64 发行**进入规划。宠物从路线图里彻底消失。

## # 小结：复盘

这次失败是实打实的：时间花了，代码归档了，宠物功能一行没上线。

但复盘下来也不是全白费：

1. **评测机制留下来了**。Creator Gate、严格的 benchmark 契约、被拒变体留痕——这套"先证明、再接受"的方法论不绑定宠物，以后选任何运行时都能用。
2. **质量底线守住了**。方案里明确拒绝姿势轮播冒充动画。如果当时松了这个口子，宠物是能"做出来"，但会变成一个我天天看着难受的残次品。
3. **停得够早**。最怕的不是失败，是失败前已经把制作管线全铺开。这次在投入正式制作之前就验证了"没有路"，止损算及时。

教训就一条：**当需求同时要求"低成本"和"高质量"时，先花时间验证这两件事之间有没有解，再决定要不要开工**。有些组合在现实里就是不存在，闷头做到最后一刻只会更亏。

宠物就此从当前产品线移除。除非哪天素材或方案有实质性的突破，否则我不打算再碰它。
