## # 前言

iOS 版打磨到能日常使用之后，最近开始处理另一个拖了很久的事：**把亦可YK 的安卓版本复刻出来。**

这里说的“复刻”不是照抄一遍界面，也不是简单把网页塞进 WebView。更准确地说，是以现在已经跑顺的 iOS 版为参照，把账号、图库、刷图、音频播放、AI 绘画这些已经验证过的产品形态，在安卓上重新做一遍。

与此同时，亦可YK 还准备加一块新能力：**一个自己的云视频库。**

先把话说清楚：这不是什么公开视频平台，**主要就是给我自己用的**，存点“学习资料”。不打算开放给所有用户，也**不提供大陆访问**。视频底层暂时选型为 [Bunny.net](https://dash.bunny.net/) 的 **Bunny Stream**。这篇就把当前思路记下来。

## # 为什么先做安卓版复刻

iOS 版这段时间已经把很多产品问题磨清楚了：哪些页面应该放在一级入口，哪些操作应该更少跳转，播放器怎么控制，刷图怎么连续浏览，通知什么时候推送才不烦人。

这些东西如果直接从零再设计一遍，很容易越做越偏。安卓版现在最重要的目标不是重新发明一套交互，而是先做到和 iOS 版**功能对齐、体验接近**。

但安卓也不是完全照搬。系统返回手势、后台限制、通知权限、文件选择、播放器行为，这些都和 iOS 不一样。尤其是视频播放这种能力，后面如果直接接进 App，就更应该用安卓侧更原生的方式处理，而不是依赖一个网页播放器。

所以安卓版的节奏大概是：

1. 先把已有核心功能复刻出来；
2. 再针对安卓的返回、通知、权限和播放器做适配；
3. 最后把视频能力作为新模块接进去。

## # 视频这块，本来就是给我自己用的

回头看，亦可YK 大部分功能的起点都是“我自己想用”：图库和刷图是为了我自己看图方便，音乐播放器是为了我自己听歌，AI 绘画也是我自己玩得最多。视频也一样，不打算做成开放平台，就是给自己存点“学习资料”。

之前说过后面会往 ASMR 和本子方向走，视频其实就是顺着这条路自然长出来的一块。

直接传公共视频平台当然最省事，但对这类内容来说不现实：

- “学习资料”这种东西放公共平台，随时可能因为内容政策被干掉；
- 播放器带着别人的品牌，推荐和审核都不归我管；
- 链接哪天失效都不知道，也没法和自己的资源库接在一起。

另一个极端是全部自建：自己上传原片、跑 FFmpeg、切 HLS、生成多码率、做封面、存对象存储、接 CDN、写播放鉴权。理论上最自由，实际上对个人项目来说就是个无底洞。

所以我说的“自己的云视频”，不是从零造一套视频管线，而是：

- 视频资源、标题、标签、分类、观看进度存在自己的后端；
- 访问权限和登录态走亦可YK 自己的系统，只有我自己能看；
- 转码、分发、播放这些底层重活交给专业服务；
- App 端只面对自己的业务接口，不直接被某个视频平台绑死。

这样它看起来和用起来都是亦可YK 里的一个私有模块，但我不用自己维护整套转码和 CDN。

**大陆访问这块反而省事。** 视频不面向大陆用户，受众基本就我自己，直接走海外节点就行，不用去折腾大陆加速、备案、兼容性那一堆破事。

## # 为什么暂时选 Bunny Stream

这次先看的是 [Bunny Stream](https://bunny.net/stream/)，后台地址是 <https://dash.bunny.net/>。

它比较符合我现在的需求：上传、转码、存储、CDN、播放器、安全控制和 API 都在同一套服务里。对一个自用项目来说，这种“开箱即用，但后端还能接得比较深”的方案，比单独拼一堆服务要现实得多。

目前比较在意的点有几个。

### 1. 转码和分发不用自己维护

上传视频之后，Bunny Stream 可以处理多分辨率转码，并通过它的 CDN 分发。官方介绍里也把转码、存储、安全和播放器放在同一个工作流里。

这正好省掉最麻烦的部分。否则我要自己处理视频队列、转码失败重试、不同码率文件、封面生成、播放列表和全球分发，工作量比业务本身还大。

### 2. API 优先，适合接进自己的后端

Bunny Stream 提供视频管理 API，也支持可续传上传（TUS）和 Webhook。这样我的后端只管保存视频业务信息，再通过 API 同步资源状态。

理想流程是：

1. 我在后台或 App 里选视频上传；
2. 后端创建视频记录并签发一次性上传授权；
3. 客户端直连 Bunny 传大文件，业务服务器不中转视频；
4. Bunny 转码完成后通过 Webhook 回调；
5. 后端更新封面、码率和入库状态；
6. App 登录后拿到授权再播放。

大文件不压在我自己的小服务器上，资源信息和权限又仍然掌握在自己后端里。

### 3. 可以不用它的默认播放器

Bunny Stream 自带可定制播放器，但我更关心的是它能不能提供 HLS 这类标准播放方式。

后续安卓端打算用 Media3/ExoPlayer 一类原生播放器直接接 HLS，让视频播放更像 App 的一部分，而不是嵌一个网页。iOS 和安卓共用同一套后端接口，各自调用平台原生播放器，结构会更清楚。

### 4. 自用场景下，基础访问控制就够了

视频内容肯定不能裸奔，但我对保护级别的要求其实很明确：**就我自己看，别让链接外泄后被人盗刷流量就行。**

热链保护（Referer/域名限制）加 Token 签名地址，基本就能满足这个场景。企业级 MediaCage DRM 那种按月收费再加按 License 计费的方案，对一个自用“学习资料”库属于杀鸡用牛刀，暂时完全不考虑。

### 5. 早期成本比较可控

Bunny Stream 的价格也是我愿意先试的原因之一。根据官方[价格页](https://bunny.net/pricing/stream/)和[文档](https://bunny.net/docs/stream)，标准转码和自带播放器不另外收费，账单主要跟着存储和流量走；高级编码和企业 DRM 才是额外成本。

自用场景量本来就不大，按使用量付费比一上来背很重的固定费用合适得多。当然，防盗链和 Token 鉴权必须第一天就开好——不然视频地址被扫到，流量费可能比我看片还积极。

## # 还需要实测的问题

选型只是第一步，不代表完全没问题。

最需要实测的是**实际播放体验**：我常用网络环境下的首屏速度、拖动缓冲和弱网表现。CDN 厂商页面上的 PoP 数量和骨干网带宽只能当参考，自己手机上点开顺不顺才算数。

另外还要注意几件事：

- 存储账单会受多码率、封面、原始文件保留策略影响，码率别开太多；
- 视频流量一旦被外链滥用，费用会涨得很快；
- App 端要处理上传中断、转码中、转码失败这些状态；
- 观看进度、断点续播这种“自己用才知道重要”的细节要补上。

所以现在只是“先选 Bunny Stream 做接入验证”，不是锁死在这一家。业务数据和播放接口都放在自己的后端，后面真要换供应商，App 端不至于整体重写。

## # 小结

当前计划可以概括成三句话：

1. **安卓版先以 iOS 版为蓝本作功能复刻，再处理安卓平台差异。**
2. **视频模块是只给我自己用的“学习资料”库，不开放给所有用户，也不提供大陆访问。**
3. **底层暂时选型 Bunny Stream，先验证上传、Webhook、鉴权播放和 HLS 原生播放这条最小链路。**

下一步先做最小闭环：后台能上传，Bunny 转码完成后能回调，后端能控制播放权限，安卓端能用原生播放器播起来。等这条链路跑通，再补播放进度、分类和标签这些自己用着舒服的细节。

继续慢慢做。
