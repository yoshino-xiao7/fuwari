## # 前言

翻了下这几天的 GitHub 动态，提交主要落在三个仓库：`dsh-codex`、`dsh-deepseek-account` 和 `deepseek-harness-desktop-yukiryou`。

它们表面上分别是模型接入、账户信息和桌面应用，实际都在做同一件事：**把原来容易堆进桌面壳里的能力拆出去，让插件自己发布、自己升级，桌面端只保留安装、验证和恢复能力。**

上一篇已经写过的项目和首发过程，这次不再重复。本文只记 8 月 28 日之后新做的几件事，以及过程中踩到的一次真实回归。

## # 新项目：把 Codex 接进 Harness

8 月 28 日新建了 `dsh-codex`，npm 包名是 `dsh-codex-community`。三天里从最初版本推进到 `1.1.1`，目前提供 ChatGPT OAuth 登录、Codex 模型、图片输入、流式文本、reasoning、usage、工具调用和会话 replay。

::github{repo="yoshino-xiao7/dsh-codex"}

对我来说，重点不是“又接了一个模型”，而是把几个容易糊弄过去的细节做完整。

### OAuth 和图片不绕开 Harness

登录在 DSH Web 的设置页完成，授权链接和验证码只有用户主动点击时才会写入剪贴板，不记录短期授权材料。

图片继续走 Harness 原生的粘贴、拖放和 attachment 流程。`read_image` 读取 HTTP(S) 图片时会限制地址、重定向、格式、大小和超时，而不是把任意远程内容直接交给模型。

### 控制项要来自真实能力

插件能设置当前会话的 Fast、传输方式、回复详略和推理摘要。Fast 和推理档位不是靠模型名字猜出来的，而是通过本机只读 RPC 获取当前 Provider catalog 暴露的能力；RPC 不可用或语义未知时就不显示，不自己补一个“看起来应该支持”的默认值。

`1.1.0` 又把这些设置做成了全局默认值，会话只保存用户明确修改过的覆盖项。这样更换默认传输方式时，不会顺手改掉已经单独配置的会话，也不会打断正在执行的请求。

### 流式恢复不能制造第二次副作用

`1.1.1` 专门修了 Codex 服务过载时的恢复逻辑：

- 输出前遇到已知服务端过载，可以按有限策略重试；
- 已经输出安全文本后，保留现有内容，提示用户稍后手动发送“继续”；
- 工具调用开始后禁止整次请求重放，避免工具被执行两次；
- 界面只显示脱敏后的中英双语提示，不透传原始服务端错误。

“自动重试”听起来很贴心，但只要请求里有工具，就可能把一次网络故障变成两次文件修改或两次外部操作。这里宁愿少自动一步，也不能假装所有流都能无损重放。

当前精确安装方式：

```sh
dsh plugin --profile web add dsh-codex-community@1.1.1
dsh web
```

## # 把账户侧栏从桌面端拆出去

第二个新仓库是 `dsh-deepseek-account`，当前版本 `0.1.8`。

::github{repo="yoshino-xiao7/dsh-deepseek-account"}

它做的事情很窄：在侧栏显示当前对话所选 Provider 对应的账户信息，并给 DeepSeek 提供官方余额页和充值页入口。它不接管登录，不读取网页 Cookie、密码或付款资料，也不在应用内完成支付。

DeepSeek API Key 只在 Host 侧通过 Harness credential service 解析；浏览器只能从 loopback RPC 拿到经过投影的余额快照。上游响应有大小限制，金额按十进制字符串处理，充值地址也固定到 DeepSeek 官方页面。

这次拆分之后，DeepSeek YukiRyou `1.0.5` 删除了桌面端原有的余额查询、今日消耗估算、IPC/preload bridge 和账户卡片。账户服务的变化不再要求整个桌面应用跟着发版——这是 Plugin-first 真正开始产生收益的地方。

### 一个 `display: contents` 引出的 0.1.8

账户插件发布后还遇到一个很具体的界面问题：当官方 Cordis Plugin 也占用侧栏 footer 时，两个入口会横向挤在一起。

`0.1.7` 尝试给 slot anchor 设置 `flex-direction: column`，规则命中了，却没有实际生效。原因是 Harness 给这个 anchor 写了内联 `display: contents`，它根本不生成布局盒，改 flex 方向自然没有用。

`0.1.8` 改为只匹配直接包含账户卡片的 `sidebar.footer.action` anchor，先恢复为真正的 flex 布局，再让入口纵向排列。回归测试也从“检查源码里有没有这段 CSS”改成实际执行样式安装并检查最终注入结果。

这个 bug 很小，但教训挺明确：**选择器匹配成功，不等于浏览器真的建立了你以为的布局。**

安装方式：

```sh
dsh plugin --profile web add dsh-deepseek-account@0.1.8
dsh web
```

## # 桌面端 1.0.5～1.0.7：插件能拆出去，也得接得回来

能力拆成插件之后，桌面端的任务变成了另一种难题：怎样把用户已经从命令行安装的插件安全接管到受管市场里，继续提供更新、停用、卸载和失败恢复。

`1.0.5` 完成了账户功能迁移，也允许验证过包名、版本、真实路径和仓库回链的外部顶层插件进入接管流程。桌面端不会直接搬目录，而是重新检查 npm 包体和依赖图，经过系统原生确认后试启动；只有新安装健康，才移除旧 profile，失败则恢复原配置。

接着事情并没有一次做对。

### 1.0.6 修了一处路径，又暴露了发布包路径

`1.0.6` 先修复 Runtime lock 文件路径，让外部插件能够完成冻结依赖图预检。真实的 `dsh-codex-community@1.1.0` 在验证时涉及 95 个 npm 制品，也顺便逼着归档检查兼容 `@types/node` 的包名根目录、字节完全一致的重复条目等现实情况，同时继续拒绝目录穿越、符号链接、大小写碰撞和内容冲突。

但这个版本又出现了更严重的回归：源码布局中的路径是对的，打包后市场插件位于 `node_modules/@dsh-desktop/market`，快照仍按源码结构寻找固定 lock，结果是**所有插件的安全预检都失败**。

### 1.0.7 修回归，也把门禁补到发布包

`1.0.7` 让 Runtime 快照显式区分源码布局和发布包布局，恢复外部插件的包体、依赖图、Runtime Peer 和冻结 lock 预检。

更重要的是，`runtime:verify` 现在会真正加载随包市场插件并读取 Runtime 快照。以前的测试证明“源码目录里能跑”，新的门禁要证明“用户下载到的应用包里也能跑”。

这一版还给主页更新入口和“关于 → 软件更新”加了原生下载百分比；更新源拿不到总大小时，就降级成不确定进度，而不是编一个假的百分比。

回头看，这次回归并不是测试数量不够。`1.0.7` 已经有 485 项单元测试和 48 项集成测试，问题在于之前缺了**发布后目录形态**这一层验证。测试多不等于边界全，真正重要的是测试对象有没有覆盖用户最终拿到的东西。

## # 小结

这几天写了不少代码，但真正完成的是一次职责重新划分：

1. **Codex 成为独立 Provider 插件**，模型、图片、传输、额度和流恢复由它自己维护；
2. **账户信息成为独立插件**，桌面端不再持有余额 bridge，也不跟账户接口一起发版；
3. **桌面应用退回平台职责**，负责验证、接管、更新、试启动和失败恢复；
4. **发布包本身进入回归门禁**，不再只证明源码工作区里的路径成立。

Plugin-first 不是把代码从 A 仓库复制到 B 仓库就结束了。真正困难的是拆完以后，版本边界、权限边界、发布边界和恢复路径还能不能说清楚。

这次也留下了一个很实用的提醒：当功能开始跨仓库协作时，验收不能只看每个仓库单独通过，还得验证它们在用户真正安装到本机后的组合状态。
